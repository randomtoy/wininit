# Security model

## Trust boundaries

The Windows service may run as LocalSystem because hostname provisioning makes
a machine-wide change. This makes every input and child process a privilege
boundary. The following are untrusted even when provided by an administrator or
cloud platform:

- metadata and user-data;
- configuration content and filesystem paths;
- Registry contents left by older or interrupted versions;
- filenames, logs, and archive entries;
- external plugin binaries, protocol messages, and output; and
- datasource media labels and filesystem structures.

The built-in NoCloud datasource reads only required `instance-id` and optional
`local-hostname` from an explicitly selected seed directory or an unambiguous
mounted `CIDATA` volume. ConfigDrive reads only `uuid` and optional `hostname`
from one selected `openstack/<version>/meta_data.json` on a local seed or
`config-2` volume. Neither opens or executes user-data. ConfigDrive may use an
explicit verified process; its trusted-code boundary is documented in
[External ConfigDrive](external-plugins.md) and ADR 0012. Identity provisioners
accept administrator-owned settings only, as documented in
[Identity and access](identity.md) and ADR 0011.

All seven logical plugins are independently disabled by default. Current
configuration disablement overrides pending state so an old checkpoint cannot
reactivate discovery or mutation.

## Privileges and ACLs

The service receives only the privileges required by its current operations.
Installed executable and default configuration should be protected against
unprivileged modification. Writable logs and future working data live under a
dedicated ProgramData directory. MSI-created root/log/plugin directories and
configuration use protected SYSTEM/Administrators ACLs. Lifecycle state lives
in a dedicated HKLM Registry key and is not
exposed directly to plugins.

External ConfigDrive does not inherit an unrestricted LocalSystem token. It
uses ordinary restricting SIDs for a second ACL check, deny-only Administrators,
low integrity, a private noninteractive desktop, disabled privileges, scrubbed
environment, local mTLS, pinned image verification, deadlines, and suspended
job assignment with one-process and memory limits. These are restrictions for
reviewed trusted code. They do not fully isolate filesystem reads or outbound
networking; an arbitrary hostile plugin is not supported.

## Sensitive data

Do not persist or log passwords, access tokens, private keys, or raw user-data.
Lifecycle error metadata records bounded operation context and codes, not input
payloads. Sanitized configuration output uses an allowlist. New secret-bearing
fields require redaction and archive tests before release.

Initial passwords come only from protected local files and are read only for
absent accounts. Existing passwords are not reset. Owned byte/rune/UTF-16
buffers are cleared without promising erasure of all OS/runtime copies.
Diagnostics redact complete account/key lists and password-file paths, archive
only `wininit.log`, and exclude configured secret-file identities even when
hard-linked under that name. Plugin output and remote error payloads are
discarded. SSH files reject hard links/reparse paths and receive protected ACLs
before atomic replacement; unmanaged key bytes survive.
Directory ACL repair uses handle-only NtSetSecurityObject, which avoids the
recursive permission propagation of SetSecurityInfo through user-controlled
hard-linked children. Native tests verify outside target ACLs remain unchanged.

Diagnostics include only allowlisted logs, build metadata, status, and
sanitized configuration. Archive names are generated by the agent; untrusted
paths are cleaned and constrained to prevent path traversal. Administrators
should inspect an archive before sending it to another party.

## Persistent state integrity

Registry state uses versioned, validated checkpoints and an active marker so an
interrupted save cannot silently become a successful lifecycle state. Unknown
schema versions, truncated state, and invalid transitions fail visibly. The
agent never falls back to the in-memory store in production after a Registry
failure.

Before platform mutation, the Registry store flushes the committed checkpoint
with `RegFlushKey`. Because this can flush and block changes elsewhere in the
hive, it is restricted to low-frequency lifecycle boundaries. Plugin state
stores only a SHA-256 input identity; it does not retain the raw hostname or
metadata required to replay an operation.

The `WininitPrivate\Provisioning` mutex is held in a Windows private namespace
whose boundary uses the Builtin Administrators SID without a session SID. A
protected DACL grants namespace and mutex access only to SYSTEM and Builtin
Administrators. It prevents an SCM service and an elevated console process—or
two differently configured elevated processes in different sessions—from
mutating the machine concurrently. A second process fails explicitly.

## Datasource and hostname controls

NoCloud discovery never picks between multiple eligible volumes. An explicit
seed directory avoids enumeration; discovery otherwise requires exactly one
mounted volume labelled `CIDATA` with an ISO9660 or FAT filesystem. Query
failures and unsupported filesystems on unrelated drives are skipped without
opening their contents. The `meta-data` file must be regular and no larger than
64 KiB; aliases, multiple YAML documents, excessive nesting, and duplicate keys
are rejected. Raw metadata is not persisted or included in diagnostics.

ConfigDrive uses the same media restrictions with the `config-2` label and
reads bounded UTF-8 JSON. Duplicate keys, excessive nesting, symlinked path
components, and invalid consumed fields fail with sanitized errors. A selected
version's invalid metadata never triggers downgrade or another datasource.
The pipeline rejects multiple available enabled sources before any provisioner
runs. It does not merge fields from different sources.

OpenStack FQDN normalization occurs explicitly in ConfigDrive: validate the DNS
name, take the lowercase first label, and leave Windows length/name validation
to the provisioner. No suffix is configured and no label is truncated. Do not
consume `user_data`, `password`, vendor/network data, or injected file paths
in the datasource; only the separate enabled PowerShell provisioner reads user-data.

Hostname input is restricted to the documented conservative ASCII label. The
provisioner refuses domain-joined rename and does not implicitly convert or
truncate an FQDN. ConfigDrive's explicit normalization happens before this
Windows-specific validation.
`reboot.policy` remains `never`; LocalSystem records a restart checkpoint but
never restarts the guest. The administrator controls restart timing.

PowerShell is a separate privileged process, independently disabled by default.
It requires allow_privileged and exact script/EXE SHA-256 pins. It reads only
the host-selected source after verifying instance/hostname, then snapshots a
bounded UTF-8 script. A flushed host journal gates execution and prevents
automatic retries. Script input travels over private stdin, never argv or an
agent payload spool; combined output is counted and discarded.

The process retains administrative provisioning access, with direct shutdown
privileges removed, a private desktop, scrubbed environment, deadlines, and a
kill-on-close job limited to eight processes and 512 MiB total/per-process. It
is trusted code, not a sandbox: approved SYSTEM code can change services or
schedule work beyond the job. The agent never reboots; exit 3010 records a
request and a service restart does not satisfy it. Windows PowerShell 5.1 is
opened only at the native System32 path. TrustedInstaller ownership/hardlinks
are allowed only for this OS-serviced interpreter, not configured plugins.

OS auditing, ScriptBlockLogging, AMSI, crash artifacts, and script-created
files are outside wininit redaction. No security/audit policy is disabled.
Review approved scripts for secrets and side effects. See
[PowerShell user-data](powershell-user-data.md) and ADR 0013.

TLS verification and integrity checks must never be disabled merely to accept
cloud metadata or make tests pass.

## Supply chain

Dependencies and build actions are kept minimal and pinned where practical.
Release workflows use minimal permissions and never expose release credentials
to untrusted pull-request code. MVP artifacts are unsigned; users must verify
published SHA-256 checksums. Code signing, provenance, and SBOM publication are
planned release-hardening work.

## Reporting

Follow [SECURITY.md](../SECURITY.md) to report vulnerabilities privately.

Production Registry state is also an authorization boundary for replay control.
A valid checksum does not authenticate a checkpoint written by an ordinary
user. Load/save validate the key and its ancestors from SOFTWARE: ownership and
mutation rights belong only to SYSTEM, Administrators or Windows servicing
(TrustedInstaller). New keys receive protected SYSTEM/Administrators ACLs.
Unsafe existing permissions fail visibly; they are never silently repaired and
state is never cleared to recover. Preserve and audit journal evidence before
an administrator repairs an existing state path.
