# Release preparation and evidence

Stage 7 is partially implemented. The automated guest suite deliberately does
not reboot or rename a machine. Stable publication still requires the broader
matrix below. No certificate, licensed Windows media, cloud credentials, or
license keys are stored in this repository.

## Build a candidate

On Windows AMD64 with Go from `go.mod`, .NET 10 and the pinned WiX toolchain:

```powershell
./scripts/package.ps1 -Version 0.1.0 -RequireClean
./tests/integration/checksums.ps1 -DistDirectory ./dist
go run ./cmd/wininit-release -dist ./dist -verify -require-clean
./tests/integration/release-bundle.ps1 -DistDirectory ./dist
```

Use a clean committed checkout for a release. Local development packages may
omit `-RequireClean`; `source_modified` records their status. `-SkipBuild` still
checks the installed build metadata and requires all five EXEs from this source
commit. Numeric versions map to the documented MSI version limits; `v0.0.0`
cannot be the candidate in the upgrade suite because its fixture is `0.0.0`.
WiX restore/compiler/binder intermediates live in each bundle's `obj` directory,
isolating baseline and candidate caches; they are not distribution subjects.

The bundle contains six binaries: the agent EXE/MSI and four plugin EXEs. MSI
installs only the agent. All seven logical plugins remain disabled by default.
Each EXE has a `*.exe.cdx.json` CycloneDX 1.6 SBOM generated by the build-time
`cyclonedx-gomod` **v1.12.0** `bin` command from its actual Go build information,
without executing the plugin. The inventory includes Go modules and the Go
standard library. Short PURLs omit generator-host platform qualifiers; the
manifest verifies the binaries' own Windows/AMD64/CGO-disabled build settings.
Module names/versions in each SBOM must match its binary, including stdlib.
Replaced Go modules require a separate reviewed inventory policy.

These are module inventories, not complete Windows/installer dependency or
license audits, vulnerability scans, or a promise that every function in a
listed module is linked. No license detection/assertion is enabled. MSI includes
the agent and default configuration; it does not have a separate complete
installer SBOM. WiX/.NET build tools and OS DLLs are outside this runtime scope.
The pinned SBOM tool is downloaded through Go module checksum verification;
it is not added to the agent module or distributed as a plugin.

`release-manifest.json` schema 1 records source commit, dirty status, version,
target, packager-reported Authenticode status and exact file hashes. Portable
`SHA256SUMS` covers the six binaries, five SBOMs and manifest (twelve entries).
Neither checksums nor later Sigstore bundles recursively hash themselves.
The builder-only `cmd/wininit-release` validates the exact subject set, binary
build information and SBOM module inventory. It is not installed by MSI and
does not verify Authenticode or publisher identity. Unknown extra files in a
local dist directory are not release subjects and are not uploaded by CI.

## Optional Authenticode signing

Signing is disabled unless both a certificate thumbprint and timestamp server
are supplied. Use an existing Code Signing certificate/private-key provider in
`CurrentUser\My` or `LocalMachine\My` and Windows SDK SignTool:

```powershell
./scripts/package.ps1 -Version 0.1.0 -RequireClean `
  -SigningCertificateThumbprint YOUR_40_HEX_THUMBPRINT `
  -CertificateStore CurrentUser -TimestampServer https://YOUR-RFC3161-SERVER
```

The five EXEs are signed before MSI construction, then the MSI is signed.
SHA-256 Authenticode signatures use HTTPS RFC 3161 timestamps. Every file must
pass `signtool verify /pa /all /tw`; nonzero exits, including warnings, fail the
build. Metadata and hashes are generated after signing. Changing signatures
invalidates plugin SHA-256 pins, so administrators must pin the final files.
No PFX passwords are accepted in argv, keys imported, or trust stores modified.

No production certificate is configured or tested. The hosted release workflow
builds **unsigned draft prereleases**; signing support is a prepared builder
path, not evidence that published artifacts are signed. Production certificate,
timestamp service and key custody validation remain required.

## Provenance and draft release workflow

Trusted numeric version tags run validation, native Windows tests, packaging,
bundle corruption tests and no-reboot acceptance. Only after those succeed does
a separate job use pinned `actions/attest` v4.2.2 with GitHub OIDC to attest
`SHA256SUMS` provenance and each EXE's SBOM. This authenticates the workflow and
exact bytes, not product compatibility or a hermetic/reproducible build claim.
Pull requests receive no attestation signing permissions. Sigstore bundles are
attached for verification. The final job verifies hashes again and creates a
**draft prerelease**, never an automatically public stable release.

After downloading a candidate from a trusted tag, authenticate the manifest
first, then verify content. Example with GitHub CLI and a Unix checksum tool:

```sh
gh attestation verify SHA256SUMS --repo randomtoy/wininit \
  --signer-workflow randomtoy/wininit/.github/workflows/release.yml
sha256sum --strict -c SHA256SUMS
gh attestation verify wininit-windows-amd64.exe --repo randomtoy/wininit \
  --predicate-type https://cyclonedx.org/bom \
  --signer-workflow randomtoy/wininit/.github/workflows/release.yml
```

Repeat SBOM verification for each plugin EXE. `--bundle PATH` selects a
downloaded Sigstore bundle instead of looking it up; online certificate/log
trust verification may still be needed. Verification must also check the
expected tag/source commit in the attestation and manifest. Plain SHA-256
checksums alone do not authenticate a publisher. A release tag has not been
created for this development change, so real tag/OIDC attestation and draft
publication are prepared but unexecuted.

## Acceptance and remaining stable-release gates

See [automated guest suite](../tests/e2e/README.md) for exact commands, ownership,
reports and self-hosted runner setup. CI uses a lower-version MSI built from the
same source as an upgrade fixture; it does not establish compatibility with a
historical release or exercise schema migration from an old executable.

| Evidence | Status |
| --- | --- |
| Go, cross-build, native Registry/SCM/process tests | Required CI |
| MSI install/ACLs/default disablement, same-source upgrade, uninstall | Automated no-reboot suite |
| LocalSystem external NoCloud/ConfigDrive/hostname and PowerShell replay/failure | Automated local-seed suite |
| Server 2022/2025 × QEMU/OpenStack no-reboot suite | Manual workflow ready; requires four administrator-provisioned guest runners |
| Fresh licensed image boot/attachment/cloud creation | Pending infrastructure and execution |
| Mounted CIDATA/config-2 media, real hostname change and reboot/resume in all cells | Pending; no reboot is performed by these scripts |
| Historical-release upgrade and rollback/failure recovery | Pending historical candidate/image coverage |
| Production certificate signing/trust/timestamp | Prepared optional path; pending certificate and validation |
| Tag/OIDC attestations and draft release publication | Prepared; pending an explicitly authorized release tag |

Keep per-cell reports with exact source/artifact hashes, Windows build, observed
model, boot timestamp, skipped cases and cleanup results. Provider labels are
operator declarations; hardware strings alone do not prove KVM acceleration or
OpenStack placement. Do not mark stage 7 complete until the remaining evidence
is collected and reviewed. Publishing/promoting a stable release is a separate
maintainer action after these gates pass.
